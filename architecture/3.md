# 1. First: what changes with DDD?

Previously we had:

```text
domain
application
adapter
```

With DDD, we start thinking in terms of **business concepts**:

```text
Invoice
InvoiceItem
Customer
Money
InvoiceStatus
InvoiceNumber
```

and potentially **business boundaries**:

```text
Billing
Customer
Product
Payment
```

The most important DDD concepts you'll encounter are:

- **Entity**
- **Value Object**
- **Aggregate**
- **Aggregate Root**
- **Repository**
- **Domain Service**
- **Domain Event**
- **Application Service / Use Case**
- **Bounded Context**

You don't need all of them immediately.

For your current project, I'd start with:

> **Entity + Value Object + Aggregate + Repository + Domain Service + Domain Events**

# 3. The biggest DDD concept: Aggregate

This is probably the first concept I'd learn deeply.

Suppose our invoice looks like:

```text
Invoice
│
├── InvoiceItem
├── InvoiceItem
└── InvoiceItem
```

DDD can treat:

```text
Invoice
```

as an **Aggregate Root**.

And:

```text
InvoiceItem
```

as part of the Invoice aggregate.

So:

```text
             Invoice
          Aggregate Root
               │
       ┌───────┼────────┐
       ▼       ▼        ▼
     Item     Item     Item
```

External code should interact with the aggregate through:

```java
invoice.addItem(...);
invoice.removeItem(...);
invoice.issue();
invoice.pay();
```

rather than directly modifying:

```java
invoice.getItems().add(...)
```

This is a major change from a typical JPA model.

---

# 4. The Invoice becomes responsible for its rules

Instead of application code doing this:

```java
invoice.setStatus(InvoiceStatus.PAID);
```

we do:

```java
invoice.pay();
```

And inside:

```java
public void pay() {

    if (status == InvoiceStatus.PAID) {
        throw new InvoiceAlreadyPaidException();
    }

    if (status != InvoiceStatus.ISSUED) {
        throw new InvalidInvoiceException(
                "Only issued invoices can be paid"
        );
    }

    this.status = InvoiceStatus.PAID;
}
```

Now the aggregate protects itself.

That's very DDD-ish.

# 5. Entity vs Value Object

Another big change is that we stop making everything a primitive.

For example, previously:

```java
private BigDecimal unitPrice;
```

DDD might introduce:

```java
private Money unitPrice;
```

Instead of:

```text
BigDecimal
```

we have:

```text
Money
 ├── amount
 └── currency
```

For example:

```java
public final class Money {

    private final BigDecimal amount;
    private final Currency currency;

    public Money(
            BigDecimal amount,
            Currency currency) {

        if (amount == null) {
            throw new IllegalArgumentException(
                    "Amount cannot be null"
            );
        }

        if (amount.signum() < 0) {
            throw new IllegalArgumentException(
                    "Amount cannot be negative"
            );
        }

        this.amount = amount;
        this.currency = currency;
    }

    public Money add(Money other) {

        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException(
                    "Currencies must match"
            );
        }

        return new Money(
                amount.add(other.amount),
                currency
        );
    }

    public BigDecimal amount() {
        return amount;
    }

    public Currency currency() {
        return currency;
    }
}
```

Now the domain can say:

```java
Money total = item.getTotal();
```

instead of manipulating raw `BigDecimal`s everywhere.

# 6. InvoiceItem becomes a real domain object

For example:

```java
public class InvoiceItem {

    private final Long id;

    private final String productName;

    private int quantity;

    private Money unitPrice;

    public InvoiceItem(
            Long id,
            String productName,
            int quantity,
            Money unitPrice) {

        if (quantity <= 0) {
            throw new InvalidInvoiceException(
                    "Quantity must be greater than zero"
            );
        }

        this.id = id;
        this.productName = productName;
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    public Money calculateTotal() {

        return unitPrice.multiply(quantity);
    }
}
```

The business rule:

```text
quantity > 0
```

is now protected by the domain object.

# 7. Aggregate Root

The Invoice could look something like:

```java
public class Invoice {

    private Long id;

    private InvoiceNumber number;

    private Long customerId;

    private InvoiceStatus status;

    private final List<InvoiceItem> items =
            new ArrayList<>();

    public Invoice(
            Long id,
            InvoiceNumber number,
            Long customerId) {

        this.id = id;
        this.number = number;
        this.customerId = customerId;
        this.status = InvoiceStatus.DRAFT;
    }

    public void addItem(InvoiceItem item) {

        if (status != InvoiceStatus.DRAFT) {
            throw new InvalidInvoiceException(
                    "Cannot modify a non-draft invoice"
            );
        }

        items.add(item);
    }

    public void removeItem(Long itemId) {

        if (status != InvoiceStatus.DRAFT) {
            throw new InvalidInvoiceException(
                    "Cannot modify a non-draft invoice"
            );
        }

        items.removeIf(
                item -> item.getId().equals(itemId)
        );
    }

    public void issue() {

        if (items.isEmpty()) {
            throw new InvalidInvoiceException(
                    "Invoice must contain items"
            );
        }

        status = InvoiceStatus.ISSUED;
    }

    public void pay() {

        if (status != InvoiceStatus.ISSUED) {
            throw new InvalidInvoiceException(
                    "Only issued invoices can be paid"
            );
        }

        status = InvoiceStatus.PAID;
    }

    public Money calculateTotal() {

        return items.stream()
                .map(InvoiceItem::calculateTotal)
                .reduce(
                        Money.zero(),
                        Money::add
                );
    }
}
```

Now the Invoice isn't just a bag of fields.

It has **behavior**.

That's an important distinction.

# 8. Anemic model vs DDD model

This is worth understanding.

### Anemic model

You might have:

```java
@Entity
public class Invoice {

    private Long id;

    private InvoiceStatus status;

    private BigDecimal total;

    // getters/setters
}
```

And then:

```java
@Service
public class InvoiceService {

    public void pay(Long id) {

        Invoice invoice =
                repository.findById(id).orElseThrow();

        if (invoice.getStatus() != ISSUED) {
            throw ...
        }

        invoice.setStatus(PAID);
    }
}
```

The entity mostly contains data.

Business behavior lives in the service.

---

### Rich domain model

DDD moves behavior into the domain:

```java
invoice.pay();
```

And:

```java
public void pay() {

    if (status != InvoiceStatus.ISSUED) {
        throw ...
    }

    status = InvoiceStatus.PAID;
}
```

So:

```text
Anemic:

Service
 ├── validation
 ├── business rules
 ├── state changes
 └── calculations

Entity
 └── data
```

versus:

```text
DDD:

Application Service
 └── orchestrates

Domain
 ├── validation
 ├── business rules
 ├── state changes
 └── calculations
```

This is one of the most important differences.

# 9. Repository changes slightly

In DDD, the repository is usually expressed in terms of the **aggregate**.

For example:

```java
public interface InvoiceRepository {

    Invoice save(Invoice invoice);

    Optional<Invoice> findById(Long id);

}
```

Notice that this interface is inside:

```text
domain
   ↓
repository
```

rather than:

```text
adapter
   ↓
repository
```

The domain/application defines what it needs.

The infrastructure implements it.

```text
                 DOMAIN
                    │
                    ▼
          InvoiceRepository
              <<interface>>
                    ▲
                    │
                    │ implements
                    │
             PersistenceAdapter
                    │
                    ▼
                 JPA
```

This is **DDD + Hexagonal Architecture** working together.

# 10. Application Service becomes thinner

With a rich domain model, your application service shouldn't contain lots of business rules.

For example:

```java
@Service
@Transactional
public class InvoiceApplicationService {

    private final InvoiceRepository invoiceRepository;

    public void payInvoice(Long invoiceId) {

        Invoice invoice =
                invoiceRepository.findById(invoiceId)
                        .orElseThrow(
                                () -> new InvoiceNotFoundException(
                                        invoiceId
                                )
                        );

        invoice.pay();

        invoiceRepository.save(invoice);
    }
}
```

The application service says:

```text
1. Find Invoice
2. Tell Invoice to pay
3. Save Invoice
```

It doesn't say:

```text
if invoice is ISSUED
and customer exists
and invoice isn't cancelled
and payment hasn't happened
...
```

Those are domain concerns.

# 11. Domain Service

Sometimes a business rule doesn't naturally belong to one entity.

For example:

```text
Can this customer receive a discount
based on:

Customer
+
Invoice
+
Customer's purchase history
```

Putting that entire rule into `Customer` might be awkward.

And putting it into `Invoice` might also be wrong.

That's where a **Domain Service** can make sense.

```java
public class InvoicePricingService {

    public Money calculateDiscount(
            Invoice invoice,
            Customer customer) {

        // complex business rule

    }
}
```

The important distinction is:

> A domain service contains **domain logic**, not infrastructure logic.

Don't create:

```java
InvoiceService
```

just because you need somewhere to put code.

Ask:

> "Does this behavior naturally belong to an Entity/Aggregate?"

If yes → put it there.

If not → consider a Domain Service.

# 12. Domain Events

DDD also gives you another very interesting concept.

Suppose:

```text
Invoice
   ↓
issued
```

Other parts of the system may care:

```text
InvoiceIssued
      │
      ├── send email
      ├── notify accounting
      ├── update reporting
      └── publish Kafka event
```

Instead of putting all of this inside:

```java
invoice.issue();
```

the domain can produce an event:

```java
public record InvoiceIssuedEvent(
        Long invoiceId
) {
}
```

Conceptually:

```text
              Invoice
                 │
                 │ issue()
                 ▼
        InvoiceIssuedEvent
                 │
        ┌────────┼─────────┐
        ▼        ▼         ▼
      Email    Kafka    Accounting
```

This becomes particularly interesting when you combine DDD with the **event-driven architecture** you've worked with before.

# 13. Bounded Contexts

This is where DDD becomes much bigger than folder structure.

Imagine your company has:

```text
Customer
Product
Invoice
Payment
Inventory
Shipping
```

You might initially think:

```text
Customer
   ↓
Invoice
   ↓
Payment
```

But DDD asks:

> Are these actually the same business model?

For example, "Customer" in Sales might have:

```text
Customer
 ├── name
 ├── address
 ├── salesLimit
 └── creditRating
```

while "Customer" in Shipping might care about:

```text
Customer
 ├── deliveryAddress
 └── deliveryPreferences
```

They don't necessarily need to be the same class.

This leads to:

# Bounded Context

For example:

```text
                    Company
                       │
        ┌──────────────┼───────────────┐
        │              │               │
        ▼              ▼               ▼
     Billing         Sales         Inventory
        │              │               │
     Invoice        Customer         Product
     Payment        Order            Stock
```

Each context can have its own model.

That's a much more important DDD concept than simply changing:

```text
entity/
```

to:

```text
domain/
```

## And one very important point for Spring Boot

A common mistake when learning DDD is thinking:

> "My domain classes should be JPA entities."

They **can** be, but they don't have to be.

You can have:

```text
Domain

Invoice
InvoiceItem
Money
```

and separately:

```text
Persistence

InvoiceJpaEntity
InvoiceItemJpaEntity
```

with:

```text
Domain
  ↕
Mapper
  ↕
JPA
```

This gives you stronger isolation.

For a serious/complex domain, I particularly like:

```text
domain
    ↓
application
    ↓
ports
    ↓
adapters
    ↓
Spring/JPA/PostgreSQL
```

rather than allowing JPA annotations to spread throughout the domain.
