# 4. Invoice domain model

```java
package com.example.invoice.domain.model;

import com.example.invoice.domain.exception.BusinessException;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public class Invoice {

    private Long id;

    private Long customerId;

    private InvoiceStatus status;

    private List<InvoiceItem> items = new ArrayList<>();

    public Invoice(
            Long id,
            Long customerId,
            InvoiceStatus status,
            List<InvoiceItem> items) {

        this.id = id;
        this.customerId = customerId;
        this.status = status;
        this.items = new ArrayList<>(items);
    }

    public static Invoice create(
            Long customerId,
            List<InvoiceItem> items) {

        if (items == null || items.isEmpty()) {
            throw new BusinessException(
                    "Invoice must contain at least one item"
            );
        }

        return new Invoice(
                null,
                customerId,
                InvoiceStatus.DRAFT,
                items
        );
    }

    public void update(
            Long customerId,
            List<InvoiceItem> items) {

        if (status == InvoiceStatus.PAID) {
            throw new BusinessException(
                    "Paid invoice cannot be modified"
            );
        }

        if (status == InvoiceStatus.CANCELLED) {
            throw new BusinessException(
                    "Cancelled invoice cannot be modified"
            );
        }

        if (items == null || items.isEmpty()) {
            throw new BusinessException(
                    "Invoice must contain at least one item"
            );
        }

        this.customerId = customerId;
        this.items = new ArrayList<>(items);
    }

    public BigDecimal calculateTotal() {

        return items.stream()
                .map(InvoiceItem::calculateTotal)
                .reduce(
                        BigDecimal.ZERO,
                        BigDecimal::add
                );
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public InvoiceStatus getStatus() {
        return status;
    }

    public List<InvoiceItem> getItems() {
        return List.copyOf(items);
    }
}
```

Notice where this rule lives:

```java
if (status == InvoiceStatus.PAID) {
    throw new BusinessException(...);
}
```

That's a **business rule**, so it belongs in the domain.

Not in the controller.

Not in the repository.

Not in the JPA entity.

# 9. Application service

Now we connect everything together.

```java
package com.example.invoice.application.service;

import com.example.invoice.application.command.CreateInvoiceCommand;
import com.example.invoice.application.command.UpdateInvoiceCommand;
import com.example.invoice.application.port.in.*;
import com.example.invoice.application.port.out.InvoiceRepository;
import com.example.invoice.domain.exception.InvoiceNotFoundException;
import com.example.invoice.domain.model.Invoice;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class InvoiceApplicationService
        implements CreateInvoiceUseCase,
                   GetInvoiceUseCase,
                   UpdateInvoiceUseCase,
                   DeleteInvoiceUseCase {

    private final InvoiceRepository invoiceRepository;

    public InvoiceApplicationService(
            InvoiceRepository invoiceRepository) {

        this.invoiceRepository = invoiceRepository;
    }

    @Override
    @Transactional
    public Invoice create(CreateInvoiceCommand command) {

        Invoice invoice = Invoice.create(
                command.customerId(),
                command.items()
        );

        return invoiceRepository.save(invoice);
    }

    @Override
    @Transactional(readOnly = true)
    public Invoice getById(Long id) {

        return invoiceRepository.findById(id)
                .orElseThrow(
                        () -> new InvoiceNotFoundException(id)
                );
    }

    @Override
    @Transactional
    public Invoice update(
            Long id,
            UpdateInvoiceCommand command) {

        Invoice invoice = invoiceRepository.findById(id)
                .orElseThrow(
                        () -> new InvoiceNotFoundException(id)
                );

        invoice.update(
                command.customerId(),
                command.items()
        );

        return invoiceRepository.save(invoice);
    }

    @Override
    @Transactional
    public void delete(Long id) {

        invoiceRepository.findById(id)
                .orElseThrow(
                        () -> new InvoiceNotFoundException(id)
                );

        invoiceRepository.deleteById(id);
    }
}
```

### Notice where `@Transactional` is

```text
Controller
    ↓
Application Service
    ↓
Domain
    ↓
Repository
```

The transaction boundary is at the **application/use-case level**.

That's generally much better than putting:

```java
@Transactional
```

on every repository method.

# 12. MapStruct

Here's an important architectural detail.

We don't want:

```text
Controller
    ↓
Invoice domain
```

We want:

```text
HTTP DTO
    ↓
MapStruct
    ↓
Command
    ↓
Application
```

For this particular conversion, we can use MapStruct for DTO mapping and explicitly create the domain items.

For example:

```java
package com.example.invoice.adapter.in.web;

import com.example.invoice.adapter.in.web.dto.InvoiceItemRequest;
import com.example.invoice.application.command.CreateInvoiceCommand;
import com.example.invoice.domain.model.InvoiceItem;
import org.mapstruct.Mapper;

@Mapper(componentModel = "spring")
public interface InvoiceWebMapper {

    default CreateInvoiceCommand toCommand(
            Long customerId,
            java.util.List<InvoiceItemRequest> items) {

        return new CreateInvoiceCommand(
                customerId,
                items.stream()
                        .map(this::toDomainItem)
                        .toList()
        );
    }

    InvoiceItem toDomainItem(InvoiceItemRequest request);
}
```

For responses:

```java
@Mapper(
    componentModel = "spring",
    imports = java.math.BigDecimal.class
)
public interface InvoiceResponseMapper {

    default InvoiceResponse toResponse(
            com.example.invoice.domain.model.Invoice invoice) {

        return new InvoiceResponse(
                invoice.getId(),
                invoice.getCustomerId(),
                invoice.getStatus(),
                invoice.getItems()
                        .stream()
                        .map(this::toItemResponse)
                        .toList(),
                invoice.calculateTotal()
        );
    }

    default InvoiceItemResponse toItemResponse(
            InvoiceItem item) {

        return new InvoiceItemResponse(
                item.getId(),
                item.getProductName(),
                item.getQuantity(),
                item.getUnitPrice(),
                item.calculateTotal()
        );
    }
}
```

The important point isn't merely "use MapStruct."

It's:

> **MapStruct belongs at the boundary where objects cross architectural boundaries.**

# 13. Controller

```java
package com.example.invoice.adapter.in.web;

import com.example.invoice.adapter.in.web.dto.*;
import com.example.invoice.application.command.UpdateInvoiceCommand;
import com.example.invoice.application.port.in.*;
import com.example.invoice.domain.model.Invoice;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/invoices")
public class InvoiceController {

    private final CreateInvoiceUseCase createInvoiceUseCase;
    private final GetInvoiceUseCase getInvoiceUseCase;
    private final UpdateInvoiceUseCase updateInvoiceUseCase;
    private final DeleteInvoiceUseCase deleteInvoiceUseCase;

    private final InvoiceWebMapper webMapper;
    private final InvoiceResponseMapper responseMapper;

    public InvoiceController(
            CreateInvoiceUseCase createInvoiceUseCase,
            GetInvoiceUseCase getInvoiceUseCase,
            UpdateInvoiceUseCase updateInvoiceUseCase,
            DeleteInvoiceUseCase deleteInvoiceUseCase,
            InvoiceWebMapper webMapper,
            InvoiceResponseMapper responseMapper) {

        this.createInvoiceUseCase = createInvoiceUseCase;
        this.getInvoiceUseCase = getInvoiceUseCase;
        this.updateInvoiceUseCase = updateInvoiceUseCase;
        this.deleteInvoiceUseCase = deleteInvoiceUseCase;
        this.webMapper = webMapper;
        this.responseMapper = responseMapper;
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public InvoiceResponse create(
            @Valid @RequestBody CreateInvoiceRequest request) {

        Invoice invoice =
                createInvoiceUseCase.create(
                        webMapper.toCommand(
                                request.customerId(),
                                request.items()
                        )
                );

        return responseMapper.toResponse(invoice);
    }

    @GetMapping("/{id}")
    public InvoiceResponse getById(
            @PathVariable Long id) {

        return responseMapper.toResponse(
                getInvoiceUseCase.getById(id)
        );
    }

    @PutMapping("/{id}")
    public InvoiceResponse update(
            @PathVariable Long id,
            @Valid @RequestBody UpdateInvoiceRequest request) {

        UpdateInvoiceCommand command =
                new UpdateInvoiceCommand(
                        request.customerId(),
                        request.items()
                                .stream()
                                .map(webMapper::toDomainItem)
                                .toList()
                );

        return responseMapper.toResponse(
                updateInvoiceUseCase.update(id, command)
        );
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(
            @PathVariable Long id) {

        deleteInvoiceUseCase.delete(id);
    }
}
```

Notice how thin the controller is.

It mostly performs:

```text
HTTP
 ↓
DTO
 ↓
Command
 ↓
UseCase
 ↓
Response DTO
```

There is no business logic.

# 15. Persistence mapper

```java
@Component
public class InvoicePersistenceMapper {

    public InvoiceJpaEntity toEntity(Invoice invoice) {

        InvoiceJpaEntity entity =
                new InvoiceJpaEntity();

        entity.setId(invoice.getId());
        entity.setCustomerId(invoice.getCustomerId());
        entity.setStatus(invoice.getStatus());

        for (InvoiceItem item : invoice.getItems()) {

            InvoiceItemJpaEntity itemEntity =
                    new InvoiceItemJpaEntity();

            itemEntity.setId(item.getId());
            itemEntity.setProductName(
                    item.getProductName()
            );
            itemEntity.setQuantity(
                    item.getQuantity()
            );
            itemEntity.setUnitPrice(
                    item.getUnitPrice()
            );

            itemEntity.setInvoice(entity);

            entity.getItems().add(itemEntity);
        }

        return entity;
    }

    public Invoice toDomain(
            InvoiceJpaEntity entity) {

        List<InvoiceItem> items =
                entity.getItems()
                        .stream()
                        .map(item ->
                                new InvoiceItem(
                                        item.getId(),
                                        item.getProductName(),
                                        item.getQuantity(),
                                        item.getUnitPrice()
                                )
                        )
                        .toList();

        return new Invoice(
                entity.getId(),
                entity.getCustomerId(),
                entity.getStatus(),
                items
        );
    }
}
```

You could also use MapStruct here, but I intentionally showed this mapper manually because of the bidirectional relationship:

```text
InvoiceJpaEntity
      ↓
InvoiceItemJpaEntity
      ↓
invoice
```

JPA relationships often require a little more care than simple DTO mapping.

Remember:


is **our application port**.

While:


is a **Spring Data implementation detail**.

# 17. Persistence adapter

```java
@Component
public class InvoicePersistenceAdapter
        implements InvoiceRepository {

    private final InvoiceJpaRepository repository;
    private final InvoicePersistenceMapper mapper;

    public InvoicePersistenceAdapter(
            InvoiceJpaRepository repository,
            InvoicePersistenceMapper mapper) {

        this.repository = repository;
        this.mapper = mapper;
    }

    @Override
    public Invoice save(Invoice invoice) {

        InvoiceJpaEntity entity =
                mapper.toEntity(invoice);

        InvoiceJpaEntity saved =
                repository.save(entity);

        return mapper.toDomain(saved);
    }

    @Override
    public Optional<Invoice> findById(Long id) {

        return repository.findById(id)
                .map(mapper::toDomain);
    }

    @Override
    public void deleteById(Long id) {

        repository.deleteById(id);
    }
}
```

Now the complete dependency chain is:

```text
                    ┌──────────────┐
                    │   REST API   │
                    └──────┬───────┘
                           │
                           ▼
                 ┌──────────────────┐
                 │    Controller    │
                 └────────┬─────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │    Input Port    │
                 └────────┬─────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │ Application      │
                 │ Service          │
                 └────────┬─────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │     Domain       │
                 │     Invoice      │
                 └────────┬─────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │   Output Port    │
                 │ InvoiceRepository│

                          │
                          ▼
                 ┌──────────────────┐

                          │
                          ▼
                 ┌──────────────────┐

                 └────────┬─────────┘

                     PostgreSQL
```

# 20. Unit testing the application service

This is where Hexagonal Architecture becomes really useful.

We can test the application without:

- PostgreSQL
- Hibernate
- Spring Boot
- HTTP
- Tomcat

We simply mock the output port.

```java
@ExtendWith(MockitoExtension.class)
class InvoiceApplicationServiceTest {

    @Mock
    private InvoiceRepository invoiceRepository;

    @InjectMocks
    private InvoiceApplicationService service;

    @Test
    void shouldCreateInvoice() {

        var items = List.of(
                new InvoiceItem(
                        null,
                        "Keyboard",
                        2,
                        new BigDecimal("50")
                )
        );

        var command =
                new CreateInvoiceCommand(
                        100L,
                        items
                );

        var savedInvoice =
                Invoice.create(100L, items);

        when(invoiceRepository.save(any(Invoice.class)))
                .thenReturn(savedInvoice);

        Invoice result =
                service.create(command);

        assertEquals(
                100L,
                result.getCustomerId()
        );

        assertEquals(
                new BigDecimal("100"),
                result.calculateTotal()
        );

        verify(invoiceRepository)
                .save(any(Invoice.class));
    }
}
```

This test is extremely fast.

# 22. Persistence integration test

For the persistence adapter, we actually want to test JPA.

A production-oriented approach is **Testcontainers**.

Conceptually:

```java
@Testcontainers
@SpringBootTest
class InvoicePersistenceAdapterTest {

    @Container
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:17");

    @Autowired
    private InvoiceRepository invoiceRepository;

    @Test
    void shouldSaveAndLoadInvoice() {

        var item = new InvoiceItem(
                null,
                "Keyboard",
                2,
                new BigDecimal("50")
        );

        var invoice =
                Invoice.create(
                        100L,
                        List.of(item)
                );

        Invoice saved =
                invoiceRepository.save(invoice);

        Invoice loaded =
                invoiceRepository.findById(
                        saved.getId()
                ).orElseThrow();

        assertEquals(
                100L,
                loaded.getCustomerId()
        );

        assertEquals(
                new BigDecimal("100"),
                loaded.calculateTotal()
        );
    }
}
```

The exact Testcontainers configuration can vary with Spring Boot version, but the architectural point is important:

```text
Unit test
   ↓
Mock output port

Integration test
   ↓
Real PostgreSQL
```

You don't need to use a mock database for everything.

# 23. Exception handler

Finally, REST errors should be handled at the adapter boundary.

```java
@RestControllerAdvice
public class InvoiceExceptionHandler {

    @ExceptionHandler(InvoiceNotFoundException.class)
    public ResponseEntity<String> handleNotFound(
            InvoiceNotFoundException exception) {

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(exception.getMessage());
    }

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<String> handleBusiness(
            BusinessException exception) {

        return ResponseEntity
                .badRequest()
                .body(exception.getMessage());
    }
}
```

Again:

```text
Domain exception
       ↓
Web adapter
       ↓
HTTP response
```

The domain doesn't know what HTTP `400` means.

# 24. Why all of this?

Compare this:

### Traditional layered architecture

```text
Controller
    ↓
InvoiceService
    ↓
InvoiceRepository
    ↓
JPA
```

with:

### Hexagonal

```text
                     Controller
                         │
                         ▼
                  CreateInvoiceUseCase
                         │
                         ▼
                ApplicationService
                         │
                         ▼
                     Domain
                         │
                         ▼
                 InvoiceRepository
                         │
                         ▼
                PersistenceAdapter
                         │
                         ▼
                      JPA
```

The second looks more complicated.

And **it is**.

That's an important point.

You shouldn't automatically use Hexagonal Architecture for every CRUD application.

# 25. When Hexagonal Architecture is worth it

I'd consider it when you have things like:

```text
Complex business rules
        +
Multiple integrations
        +
Large application
        +
Long expected lifetime
        +
Multiple developers
```

For example:

```text
                    ┌── REST
                    │
                    ├── Kafka
                    │
                    ├── Scheduled Job
                    │
                    ▼
             ┌──────────────┐
             │              │
             │   Invoice    │
             │    Domain    │
             │              │
             └──────────────┘
                    ▲
                    │
             ┌──────┴──────┐
             │             │
        PostgreSQL       Redis
```

Your business logic doesn't need to know which one triggered it.

# 26. One particularly important distinction

Since you're learning Spring Boot, I would remember these three things:

### `@Entity`

```java
@Entity
class InvoiceJpaEntity
```

is an **infrastructure concern**.

### `@Service`

```java
@Service
class InvoiceApplicationService
```

is an **application/infrastructure mechanism** used to wire the application service into Spring.

### `Invoice`

```java
class Invoice
```

is your **domain model**.

Ideally:

```text
Invoice
   │
   ├── knows business rules
   ├── calculates totals
   ├── validates invariants
   │
   └── does NOT know
       ├── Spring
       ├── JPA
       ├── PostgreSQL
       ├── HTTP
       └── Kafka
```

That's really the heart of Hexagonal/Clean Architecture.

## The mental model I'd use

When designing a new feature, ask these questions in order:

```text
1. What is the business rule?
             ↓
2. What does the use case need to do?
             ↓
3. What input does the use case need?
             ↓
4. What external resources does it need?
             ↓
5. Define output ports for those resources.
             ↓
6. Implement those ports using JPA/Kafka/REST/etc.
             ↓
7. Add adapters for REST/Kafka/etc.
```

So instead of starting with:

> "I need an `InvoiceController`."

start with:

> **"What does my business need to accomplish?"**

That shift in thinking is probably the biggest difference between ordinary Spring Boot development and Clean/Hexagonal Architecture.
